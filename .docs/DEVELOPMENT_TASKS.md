## 开发 Agent 接入步骤

1. 先读 [文档入口](README.md)、[待决策清单](PENDING_DECISIONS.md)与 [Git 协作](CONTRIBUTING.md)，检查 `git status`，保留其他任务的未提交修改。
2. 根据用户本轮目标选定本文任务 ID；未指定任务时，先定位最早尚未完成且依赖满足的交付批次，说明本轮承接范围。本文提供开发顺序，不自动授权执行后续全部批次。
3. 阅读对应模块的规则来源、任务行及所依赖的接口约定。只加载相关项目方案段落；涉及页面时另读 [前端规范](FRONTEND_DESIGN.md)与 [原型边界](prototype/README.md)，操作环境时读 [开发环境](DEVELOPMENT.md)。
4. 核实依赖任务的代码、实际验证及交接记录。模块依赖表示需要相关能力或接口，不要求上游模块所有任务先完成；替身与合成数据可支持局部开发，但不能据此宣布真实接入或整条流程已验收。
5. 将承接任务改为“进行中”，按有限范围实现、迁移和验证。跨模块修改标明主责任务与协作任务，避免复制第二套保存、预算、检索权限或调度逻辑。
6. 按本文件末尾的完成条件更新任务状态与实施记录；产品行为有新决策时，按 README 同步主方案、决策记录、待决清单和变更记录。纯实现进度不新增产品决策编号。

任务 ID `Mxx-yy` 长期稳定；交付批次用 `B01`—`B09`；联调检查用 `X01`—`X11`，均不占用产品决策的 D 编号。表中批次是开发组织安排，可随实现依赖调整并说明理由。状态统一为“待开发 / 进行中 / 待验证 / 已完成 / 阻塞”；“阻塞”须记录具体依赖及可继续的部分。

## 模块总览与数据归属

部署沿用模块化单体：API 与 worker 共用业务代码，PostgreSQL 保存关系数据、索引及持久化任务。模块是代码与职责边界，主、作者、角色 Agent 是调用职责；不将其拆成独立服务。

### 实现粒度与唯一主责

M 编号用于需求定位，不要求对应 12 套独立包结构。M04/M05/M06 可放在同一创作领域内，M07/M08 可放在同一记忆与检索领域内，通过普通函数和同一数据库会话协作。目录、函数和数据访问层随实际需求建立，不按每个模块预建接口、服务、仓储全套模板。

| 操作 | 唯一主责 | 其他模块的协作范围 |
| --- | --- | --- |
| 切换作品的用户操作 | M04 保存当前作品及明确继续时的完结状态变化 | M04-04 调用 M09 的切换处理入口；M04 不另写排队、取消或接续算法 |
| 切换后的任务处理 | M09 处理旧未开始自主任务失效、旧任务收尾和新作自主接续 | M09-06 读取已保存作品状态；不再次修改当前作品标记；重启后的启动检查仍读取当前状态 |
| 作者结果正式采用 | M05 提供单一采用入口并控制同库事务 | M06 提供经检查的结果；M04/M07 提供必要事实读写，M08 提供旧索引失效，M09 提供取消状态及采用标识；协作模块不各自提交同一采用事务 |
| 上下文构建 | M03、M06 分别负责主 Agent、作者/角色的最终上下文 | M08 提供权限过滤、资料召回、文本预算和引用辅助，不再维护另一套人格或创作要求 |

正文、版本、采用标识、对应正式事实及旧索引失效在同一数据库的短事务中完成；模型调用、向量生成和 QQ 发送在事务外执行。M09 的取消生效与 M05 的采用通过数据库中一致的先后规则处理，不引入用户编辑锁、补偿流程或跨模块事件总线。向量生成失败或通知失败各自处理，不回滚已经采用的正文。

### 按来源和执行阶段检查

下面映射主方案 D01/D02/D13/D14 的已有规则。实现采用少量明确条件分支，不建立通用规则引擎。账号有效、用户/作品归属、取消状态和调用预算在对应执行/保存入口检查；网页阅读和手动保存不要求模型预算。

| 行为 | 开始或继续的条件 | 不应施加的额外限制 |
| --- | --- | --- |
| 回复正常 QQ 新消息 | 已完成初始化，去重并按可信时间记录；按顺序理解，模型回复受调用额度限制 | 不要求已经有当前作品、创作共识或未完结作品；正常闲聊可独立进行 |
| 启动新的自主创作 | 实际准备执行时检查当前作品未完结、已有基本共识、有效 QQ 活跃、推进量/节奏、预算及旧任务收尾状态 | 不以提前入队替代启动检查，不要求用户逐段批准 |
| 用户明确指定的单次局部重写，包括网页操作 | 目标作品、范围和有效要求明确；归属正确、账号可用，遵守同作品顺序和调用预算 | 不要求作品为当前或未完结，不要求仍在 24 小时活跃期；不为了局部修订重开整部作品的共识流程，不修改当前标记或完结状态 |
| 已实际开始的有限创作继续执行 | 保持原作品、原范围和任务累计预算；未被取消、账号有效；每次新模型调用仍检查剩余额度 | 不因跨过 24 小时或当前作品切换而中断、拒绝采用；完成后不自行接续旧任务 |
| 系统自动重试 | 沿用原任务标识、有限范围和剩余预算；取消不重试，已采用不重复采用，未知外部结果先核对；未实际开始的自主任务仍检查启动资格，已开始任务沿用有限收尾规则 | 不借重试创建全新预算、扩大工作范围或恢复已取消任务 |
| 最终生成失败后的用户手动重试 | 保留原失败记录，按原目标/原作品创建新任务，使用最新已保存内容并另记消耗；本次按用户明确委托处理 | 不因原任务曾是自主任务而自动恢复持续创作；不把通知失败或未知外部结果当成最终生成失败 |
| 主动话题生成与发送 | 分别检查活跃期及对应联系设置；发送前再次确认免打扰、频率和开关，生成调用受预算限制 | 不沿用“创作已开始可收尾”的例外在暂停后主动发消息；用户委托结果通知仍按 D03 单独处理 |

取消与停用后拒绝新调用及迟到采用；预算不足只阻止新的模型调用，已有完整结果仍可按正式采用规则保存。主动取消生效前已保存的正文保留。以上必要检查与用户并发编辑保护分别处理，不增加编辑锁、自动合并或额外审批。

## 跨模块接口与执行边界

以下是需要在实施任务中落实的业务约定，不要求现在建立全部 API、数据库表或通用事件框架。首个实现该能力的任务记录实际入口和数据结构，后续任务复用。

| 约定 | 主责与调用方 | 最少需要表达的信息及行为 |
| --- | --- | --- |
| 正常用户消息 | M02 → M03、M09 | 用户/LISA、事件唯一标识、可信时间、消息内容与类型；初始化服务指令不混作正常交流；去重后计时，理解新消息后才重新安排自主行为 |
| 创作委托 | M03 或 M11 → M09 | 用户、固定目标作品、来源、目标、有限范围、有效要求和输入引用；查看页切换不能改写已有任务归属 |
| 资料读取 | M03/M06 → M04/M07/M08 | 用户、项目、用途、角色知识范围、文本预算；稳定人格/约束与短摘要/召回资料分层提供 |
| 模型调用 | 全部调用方 → M10 | 调用归属、用途、任务累计预算、每日额度与在途记录；发出前检查取消/账号停用及额度，不绕过统一入口 |
| 正式采用 | M06 → M05 的单一入口，读取 M09 状态，使用 M04/M07/M08 数据操作 | 按“实现粒度与唯一主责”用同库短事务保存；取消先后/采用防重由一个入口处理；向量与通知在提交后执行，失败不回滚正文 |
| 当前作品切换 | M04 保存状态 → M09 处理调度 | M04 不等待旧任务或发送结果；M09 负责旧未开始自主任务失效及收尾/接续，启动检查以已保存的当前标记为准；两模块不重复实现同一调度逻辑 |
| 发送与通知 | M03 或任务通知流程 → M02，主动联系检查 M09 | 消息类别、内容、关联任务、发送状态；用户委托结果通知按 D03，自主分享受当前联系限制；采用与送达独立记录 |
| 记忆/聊天删除 | M07 → M03/M08 | 指明删除对象和范围；记忆排除与原文删除分开；保留记忆的来源状态准确，检索与上下文都遵守排除 |
| 账号整体删除 | M01 → 所有相关模块 | 先停用、停止任务和发送，再清除关联个人数据；每模块提供清理范围，迟到结果及重试不得复活账号内容 |

任务结束状态、正式采用状态和发送结果分别表达；无需因此建立三套状态机框架。M09 按 [来源与阶段](#按来源和执行阶段检查)检查任务资格，M10 控制每次新模型调用，M05 在单一入口落实最终保存边界。自主任务的活跃、当前作品和完结条件不机械施加到手动重写及旧任务收尾，检查也不扩展成用户并发编辑保护。

B04 已落地的接续入口：`lisa/works.py` 提供 `create_writing_task`、`save_chapter`、`adopt_result` 与 `invalidate_index`；`lisa/author.py` 组织固定作品/章节的有限调用，`lisa/dialogue.py` 接收有本批用户原话依据的意见和委托，`lisa/queue.py` 为聊天与作者使用独立队列。作品资料的 `Project.index_revision` 与正文的 `Chapter.version` 是 B05 索引有效性依据，保存时同事务推进；B05 检索必须比较来源当前版本，不能返回旧版本切片。当前尚未建立向量索引，不把版本标记当作完整检索实现；生活事实已复用下述 Memory 结构。

B05 当前接续入口：`lisa/memory.py` 的 `adopt_candidates` 采用有本批用户原文依据的候选，`memory_context` 提供按用户/项目/用途过滤的有效记忆，`usable_chat_clause` 排除已删除或禁用的近期原文。`MemoryUse` 只保存记忆与实际使用它的聊天任务关系，并沿本轮实际提供的历史消息传递；纠正、删除或用途调整排除来源所在对话批次及引用过它的后续批次，不清空无关历史。`Account.memory_revision` 与账号行锁使管理操作后到达的旧模型结果不再采用；作者快照不复制记忆，每次尝试重新读取。聊天删除清空原文和对应助手投递副本，记忆来源保留删除标记。尚无向量切片；M08 接入时须沿用这些过滤及来源版本规则，不另建事实副本。

B05 日记与生活接续：`lisa/life.py` 在现有 `Memory` 上区分虚拟事件与梦境，保留发生时间和来源。聊天正式回复与日记 `adopt_result` 同事务采用事件，后者关联实际 `ChapterVersion`；未采用结果、计划、想象、角色经历与稳定背景变更不写成已发生事件。`LifeShare` 记录待发送的明确分享及记忆修订号，只有 `finish_delivery` 确认 `sent` 才更新 `shared_at`；内容纠正后旧发送不能给新条目标记已分享。日记作者的近期原文按来源版本排除已纠正/删除的生活来源，每次重试重新检查，明确局部重写目标仍可使用。已有正文及独立摘要/剧情状态的语义维护继续由用户负责，不自动联动改写。
